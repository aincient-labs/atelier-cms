---
title: "When something's wrong"
description: "Run a checkup on your Atelier — and let it repair most problems for you"
---

Atelier runs on your own computer, which means when something breaks, the answer is usually
on your machine rather than on a server you can't reach. The manager has a **checkup** that
looks at everything in order and tells you what it found — and can repair most of it for you.

## Run a checkup

**In the desktop app**, go to **System → Troubleshoot** and choose **Run a checkup**. You'll get
a list grouped into *your computer*, *Atelier itself*, and *your website*, with a note under
anything that needs attention. If the problems are ones Atelier can fix, a **Repair what you
can** button appears.

**In the terminal**, the same checkup is one command:

```bash
atelier doctor
```

That only looks — it never changes anything. To repair what it found:

```bash
atelier doctor --fix
```

## What it checks

The checkup works outward-in, because a problem in one layer makes the next one impossible to
judge. If it can't get past a layer, everything below is marked **skipped** rather than failed —
"we couldn't look" and "we looked and it's broken" are different answers, and you'd chase the
wrong thing if they looked the same.

## What a repair does

Repairs go from gentlest to strongest, and stop as soon as your site is well again — so if
clearing a cache was all it took, nothing further runs.

<Steps>
  <Step title="Put back missing setup files">
    If one of Atelier's own files is damaged, it's rewritten. Your old file is kept alongside
    rather than deleted, in case you'd customised it.
  </Step>
  <Step title="Start Atelier, and wait for it">
    Then it waits until your site genuinely answers, rather than assuming it's ready the moment
    it starts.
  </Step>
  <Step title="Clear the caches">
    The single most common cure for a site that's behaving strangely after an update.
  </Step>
  <Step title="Finish any half-applied update">
    If an upgrade stopped partway, this completes it.
  </Step>
  <Step title="Repair your uploads folder">
    Occasionally a restore leaves your images owned by the wrong account, which quietly breaks
    new uploads while everything else looks fine.
  </Step>
  <Step title="Run Atelier's self-repair">
    The strongest step. It takes a snapshot of your site first and puts it straight back if the
    repair doesn't help.
  </Step>
</Steps>

<Note>
  **A repair never deletes anything.** Every step is reversible — the worst case is that it
  takes a few minutes and doesn't help. Removing Atelier, reinstalling it, and restoring a
  backup are *not* part of a repair; if one of those is what you need, the checkup says so and
  leaves the decision to you.
</Note>

## When an action stops partway

Updates, backups, restores and exports show their steps as rows of blocks while they run. If
one stops, the window stays open on the step that failed (marked red), with the error and the
log underneath. Choose **Copy report** to copy what ran, which step failed, how long each step
took and the end of the log. Paste that into your report.

## An update or start stops at "Starting the containers"

Docker sometimes leaves part of your site half-started after your computer sleeps or Docker
restarts. Atelier clears it and starts once more by itself, keeping your data. If it still says
**Docker couldn't start your site**, quit and reopen Docker Desktop, then choose **Update** (or
**Start**) again. Your site's data is safe.

If Docker has left your site's network half connected, so the site can't reach its database,
Atelier says to restart Docker, and **Run a checkup** reports it. Click **Restart Docker** (the
button names the app you run it in: Docker Desktop, OrbStack, Colima or Rancher Desktop). Atelier
lists everything else running in Docker that the restart will stop, asks first, restarts Docker,
waits for it to answer, and starts your site again. On the command line: `atelier docker restart`.

OrbStack restarts only its Docker engine (`orbctl restart docker`), so your OrbStack Linux machines
keep running. Colima restarts the profile you use, not only the default one.

If part of your site has lost its connection to the network altogether, **Run a checkup** says so
and starting the site fixes it: Atelier reconnects it and restarts the site. No Docker restart is
needed.

On Linux with Docker Engine, Atelier can't restart Docker for you. Run
`sudo systemctl restart docker`, then start the site again.

If part of your site is disconnected, an update refuses until **Start your site** reconnects it.

## Not enough disk space

Atelier checks free space in two places: your computer's disk, where your backups are saved, and
Docker's own disk, where your site's database lives. **Run a checkup** warns below 5 GB. Below
2 GB, updates are refused. Choose **Free up space** (**System → Disk space**) to remove what
Atelier no longer needs. Docker's disk is read from inside the running site, so it shows
"unknown" while the site is stopped.

If your computer's disk fills up while a backup is being saved, Atelier says so, instead of
giving a vague error.

## Out of memory

When Docker stops part of your site because it ran out of memory, Atelier says so. It also says
where to give Docker more memory: in Docker Desktop, OrbStack, Colima or Rancher Desktop,
whichever runs Docker on your computer. **Run a checkup** shows how much memory Docker has and
warns below 4 GB. It also warns if Docker stopped part of your site for lack of memory in the last
day. Until the site runs again, an update refuses and tells you why.

## "Your site's database was removed"

If the database was removed from Docker, Atelier no longer starts your site as a new, empty one.
Start stops and names your latest backup. Go to **Backups** (it works while the site is stopped)
and restore it, or run `atelier data restore <file>`. A database you erased yourself (**Remove and
erase**, or `atelier app down --wipe`) still starts as a fresh site.

## Your site is busy

Only one operation runs on a site at a time. The app and `atelier` commands share this: an update,
a backup, a restore, a start or stop, and so on. If you start a second one, Atelier refuses and says
what is already running, for example "Your site is busy: an update started 2 minutes ago is still
running." Wait for it to finish, then try again. In the terminal, `atelier` exits with code 6.

If the app or the terminal that ran it crashed, the site is free again straight away. There is
nothing to unlock.

## A failed update leaves a log

After a failed update, Atelier saves what every part of your site logged to
`<site folder>/logs/update-<date>-<time>.log`, and the error names the file. For the default site,
that folder is `~/.atelier`. Atelier keeps the newest 10. Passwords and keys are left out. Attach the
file when you ask for help.

## An update didn't finish

If a multi-step update stopped partway, **Home** shows **Continue update** and
`atelier app check-update` says the update didn't finish. Choose **Continue update**: it carries on
to the version the update was heading for. Your before-update backup and old versions are kept
until it has worked.

## If it still isn't fixed

<Steps>
  <Step title="Restore a backup">
    If your site itself is damaged rather than just stuck, go to **Backups** and restore the
    most recent one. See [Back up and restore](/backups).
  </Step>
  <Step title="Report it">
    Include the checkup's output — from the terminal, `atelier doctor --json` gives a complete
    report you can paste in — and, if an action failed, its **Copy report** text, plus the update log from `logs/` if an update failed. Add the **Atelier version** too: the desktop app shows it under **System → Your
    installation**, and `atelier app status` prints it.
  </Step>
</Steps>

<Tip>
  The checkup is safe to run anytime, and safe to suggest to someone else — on its own it only
  reads. Nothing changes until you ask for a repair.
</Tip>
